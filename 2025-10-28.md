## What I Learned Today

### Core Database Concepts
- **Relational vs Non-Relational Databases**
  - SQL databases use tables with relationships (like interconnected spreadsheets)
  - NoSQL databases use flexible documents (like filing cabinets with labeled drawers)
  - DynamoDB is NoSQL - optimized for speed and scale, not complex queries

### How DynamoDB Actually Works
- **Hash Functions for Direct Lookups**
  - DynamoDB doesn't "search" - it calculates exact locations using hash functions
  - Partition key → hash function → exact server location
  - Result: 5-10 millisecond lookups regardless of table size
  - This is fundamentally different from SQL's row-by-row searching

### Partition Keys and Table Design
- **Partition key = unique identifier for direct access**
  - For URL shortener: `short_code` is partition key (what you know when looking up)
  - Not `long_url` (that's what you're trying to find)
  - Each partition key value must be unique unless you have a sort key

### Critical Behavior: put_item Overwrites
- **Learned the hard way:** `put_item()` with same partition key = complete overwrite
  - If item exists with `short_code='abc123'`, second `put_item` replaces it entirely
  - Previous data (click_count, etc.) is GONE
  - Only one item per partition key value (unless using sort keys)

### Atomic Operations for Concurrency
- **ADD vs SET for counters**
  - `ADD click_count :inc` - Atomic increment, prevents race conditions
  - `SET click_count = :val` - Overwrites value, loses clicks with concurrent updates
  - DynamoDB handles atomic operations internally - no data loss

### Query vs Scan Performance
- **Query:** Uses partition key, fast and cheap (milliseconds)
- **Scan:** Reads entire table, slow and expensive (seconds/minutes)
- Rule: Always query by partition key when possible

### Global Secondary Indexes (GSI)
- **Purpose:** Create alternate access patterns
  - Main table: partition key = `short_code` (lookup URLs)
  - GSI: partition key = `user_id` (find all URLs by user)
  - Can sort within partition using sort key (e.g., by `click_count`)

### DynamoDB Strengths and Limitations
- **Excels at:**
  - Key-based lookups (instant access)
  - Massive scale (millions of items, same performance)
  - Concurrent updates (atomic operations)
  
- **NOT good at:**
  - Global sorting across all items
  - Complex queries with JOINs
  - Aggregations across entire table
  - These are where SQL/RDS shines
