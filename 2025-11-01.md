**Business Problem:** E-commerce company receives 10MB+ product images from suppliers. Large files cause slow page loads (hurting conversion rates) and high storage costs.

**Solution Architecture:**
```
User/Supplier → S3 (originals/) → Lambda (resize + optimize) → S3 (processed/)
                      ↓

```

**Services Integrated:**
- **S3:** Two-folder pattern (originals/ + processed/) for source of truth preservation
- **Lambda:** Python 3.12 + Pillow library, 512MB memory, 60s timeout
- **IAM Role:** Least-privilege permissions (GetObject on originals/, PutObject on processed/)

**Architecture Decisions:**
- Event-driven (async) vs request-response (sync) pattern
- Two-folder approach prevents data loss if processing fails
- File size limit: 10MB max (Lambda memory constraints)
- Output format: Always JPEG (web optimization, loses transparency)
- EXIF stripping: Privacy + 30% file size reduction

**Cost Analysis:**
- Traditional EC2 (t3.micro): $9.50/month fixed cost
- Serverless (Lambda + S3): $0.28/month for 1,000 images
- **Savings: 97% cost reduction** (scales better at low/medium volume)

## Key Technical Concepts Learned

### 1. Event-Driven Architecture
S3 can directly trigger Lambda via event notifications (no EventBridge needed). When object is uploaded to `originals/`, S3 sends event to Lambda containing bucket name and object key. Lambda processes asynchronously in background.

**Critical insight:** Must use prefix filter (`originals/`) to prevent infinite loops. Without filter, Lambda processing output to `processed/` would trigger Lambda again, creating runaway execution.

### 2. Synchronous vs Asynchronous Patterns
**Project #2 (URL Shortener) - Synchronous:**
- User → API Gateway → Lambda → DynamoDB → Response (immediate)
- User waits for result
- Use case: Need instant response (banking, gaming, real-time apps)

**Project #3 (Image Processor) - Asynchronous:**
- User → S3 upload → Confirmation (immediate)
- Lambda processes in background (event-driven)
- Use case: User doesn't need to wait (batch processing, background tasks)

### 3. Pillow .thumbnail() Behavior
```python
image.thumbnail((800, 600), Image.Resampling.LANCZOS)
```
- Shrinks images LARGER than 800x600 to fit within box
- Leaves images SMALLER than 800x600 unchanged (no upscaling!)
- Maintains aspect ratio (4000x3000 → 800x600, but 4000x2000 → 800x400)
- Prevents quality degradation from upscaling small images

### 4. IAM Least-Privilege Design
Lambda role needs THREE separate permissions:
1. `s3:GetObject` on `originals/*` (read uploads)
2. `s3:PutObject` on `processed/*` (write results)
3. CloudWatch Logs permissions (debugging)

**Why separate?** If Lambda is compromised, blast radius is limited. Cannot delete originals, cannot write to wrong folder, cannot access other AWS resources.

### 5. Lambda Resource Limits
- **Memory:** 512MB allocated (image processing is memory-intensive)
- **Timeout:** 60 seconds (10MB images process in ~3-5 seconds)
- **Concurrency:** 1,000 per region (AWS throttles excess, retries automatically)
- **Ephemeral storage:** 512MB /tmp (using BytesIO instead for efficiency)

### 6. S3 Versioning for Recovery
If `processed/product.jpg` is accidentally deleted:
- With versioning: Delete marker created, previous versions retrievable
- Without versioning: File permanently lost
- Backup strategy: Can always reprocess from `originals/` (source of truth)

## Mistakes I Made Today

### 1. CloudFront Invalidation Misunderstanding (Answer 1 - Reflection Question)
I incorrectly used CloudFront invalidation as an example of asynchronous architecture. Claude corrected me: CloudFront caching isn't the defining characteristic of async patterns. The real difference is whether the user waits for processing (sync) vs processing happens in background (async).

### 2. Pillow .thumbnail() Misconception (Answer 2 - Knowledge Check)
I thought a 100x100 image couldn't be changed to 800x600 because of "fixed input." Claude explained: `.thumbnail()` intelligently AVOIDS upscaling small images to prevent quality loss. This is a feature, not a limitation.

### 3. Overconfidence in "It's All Just Work" (Answer 2 - Reflection)
I dismissed the difficulty of Day 21 by saying "it's all just work." Claude pointed out this sounds overconfident in interviews. Better answer: "Probably the S3 trigger configuration, because event-driven architectures are new to me."

### 4. S3 Write Persistence Misunderstanding (Answer 2 - Knowledge Check)
I thought processed images were saved to "cache" if Lambda timed out. Claude corrected: S3 writes are NOT transactional. If Lambda completes `put_object()` but times out after, the image STAYS in S3. If Lambda times out BEFORE `put_object()`, the in-memory processed image is LOST forever (RAM is destroyed).
