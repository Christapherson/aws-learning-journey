### Part 2: TAM Troubleshooting Scenario
Practiced Technical Account Manager skills by building and solving a real customer scenario from scratch.

**Customer Problem:** "My EC2 instance can't access my S3 bucket - getting 'Unable to locate credentials' errors."

**Investigation Process:**
- Verified AWS CLI was installed
- Checked for credentials file (~/.aws/) - not found
- Checked environment variables - none set
- **Key discovery:** Learned about IMDSv1 vs IMDSv2
  - Simple `curl` to metadata endpoint returned nothing
  - Required token-based authentication for IMDSv2
  - AWS CLI automatically handles IMDSv2

**Root Cause:** No IAM role attached to EC2 instance

**Solution Implemented:**
1. Created IAM role `EC2-S3-Access-Role` with `AmazonS3ReadOnlyAccess` policy
2. Attached role to instance via Console (Actions → Security → Modify IAM role)
3. Verified role attachment using IMDSv2 token method
4. Tested S3 access - successfully listed buckets and downloaded files

### Technical Depth
**IMDSv2 Token Authentication:**
```bash
# Get session token
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# Use token to query metadata
curl -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/iam/security-credentials/
```

**Why this matters:** IMDSv2 prevents SSRF (Server-Side Request Forgery) attacks by requiring PUT request for token before GET requests work. Newer instances default to IMDSv2. This explains why simple curl commands fail but AWS CLI works.
